## B. Project Architecture Map



This is a Next.js 16 (App Router) storefront for Mathuram Foods, backed by its **own Postgres database** (Prisma 7, driver adapters) as the source of truth — not by live ERPNext calls. ERPNext is treated as an external system that gets synced to asynchronously, matching your stated plan to launch standalone first:



```

Browser

 ↓

Next.js App Router (src/app) ── pages + /api route handlers

 ↓

NextAuth v4 (Google OAuth only, database session strategy)

 ↓

Application services (src/lib/core/application — OrderService, InvoiceService, PricingService)

 ↓

Repositories (src/lib/repositories) ─┬─ intended sole Prisma access point (see Critical/High #3)

                                       │

 Postgres (Prisma 7 + @prisma/adapter-pg) ←┘

 ↓

Outbox (OutboxEvent) → BullMQ (Redis) → Workers (Dockerfile.worker, separate process)

 ↓

External Services

  ├── ERPNext/Frappe (FrappeClient — REST, HMAC-verified inbound webhooks)

  ├── Razorpay (payments — HMAC-verified webhooks, constant-time compare)

  ├── Shiprocket (shipping webhooks)

  ├── WhatsApp (order notifications, abandoned-cart webhook)

  ├── AWS S3 (media storage)

  └── Sentry (client/edge/server error tracking)

```



The intended layering is documented in `src/lib/ARCHITECTURE.md` (domain → core/application → repositories → infrastructure → app/api, transactional outbox for events, `ApiError`/`withErrorHandler` for errors, a Pino-backed `Logger` for logging). Most of the codebase follows this. The two places it doesn't (API routes querying Prisma directly, and the logger duplication) are documented as findings below rather than asserted from the doc alone — I verified both against the actual source.



Two small doc/code drifts, for completeness: `ARCHITECTURE.md` places domain entities at `src/lib/domain/`; the actual path is `src/lib/core/domain/`. The doc also lists Stripe as infrastructure; there is no Stripe SDK, env var, or reference anywhere in the repo — payments are Razorpay-only.

## C. Critical Issues



### ISSUE-001: Admin panel is unreachable — NextAuth session strategy is incompatible with the middleware that gates it

**SEVERITY:** CRITICAL

**CATEGORY:** Authentication / Broken Integration

**AFFECTED FILES:** `middleware.ts`, `src/modules/auth/infrastructure/authOptions.ts`, `src/app/admin/login/page.tsx`

**ROOT CAUSE:** `authOptions.ts` sets `session: { strategy: "database" }` (a deliberate choice, per its own comment, "Switched to database for authorization revocation" — good instinct for instant session revocation). But `middleware.ts` protects `/admin/:path*` and `/api/admin/:path*` using `withAuth` from `next-auth/middleware`, which reads `req.nextauth.token` via `getToken()`. **NextAuth v4's `withAuth`/`getToken()` only supports the `"jwt"` session strategy** — this is stated directly in NextAuth's own docs and is a well-documented, longstanding limitation:

  - NextAuth's own docs: *"the withAuth middleware only supports 'jwt' as s[ession strategy]"*

  - A NextAuth maintainer/community response on this exact scenario: *"you can't use withAuth if you're using a session database strategy. It only works with a jwt session strategy."*

  - A detailed write-up of the exact symptom: *"the middleware tries to retrieve the session token (JWT)... but when using the database session strategy, this token doesn't exist, and getToken returns null. This means that even if you sign in successfully, the middleware will think you're not signed in."*



  With `getToken()` always returning `null`, `isAuth` in `middleware.ts` is **always `false`**, for every request, regardless of whether the visitor is actually a signed-in admin.

**IMPACT:** `admin/login/page.tsx` calls `signIn("google", { callbackUrl: "/admin" })`. After a real admin successfully completes Google OAuth, NextAuth redirects the browser to `/admin` — and the middleware immediately bounces it back to `/admin/login`, because it (incorrectly) sees no token. This is a **login loop**: nobody, including legitimate ADMIN/MANAGER users, can reach the admin dashboard, product management, order management, inventory, or any other `/admin/*` or `/api/admin/*` functionality through normal navigation. Note the direction of the bug: it fails **closed** (locks everyone out) rather than open, so it is not an unauthorized-access vulnerability — it's a total-lockout functional bug. Separately, `src/app/admin/layout.tsx` and `src/lib/auth/rbac.ts` **do** implement correct, working authorization via `getServerSession()` (which is not JWT-restricted) — but that code never gets a chance to run, because the broken middleware redirects before the request reaches it.

**RECOMMENDED FIX:** Pick one: (a) switch back to `session.strategy: "jwt"` and accept the revocation trade-off the code comment was trying to avoid; (b) remove `/admin` and `/api/admin` from the middleware `matcher` entirely and rely solely on the already-correct `getServerSession`/`rbac.ts` checks in `admin/layout.tsx` and each admin API route (verify every admin API route actually calls `checkApiAdminOrManager()` — most do, per this audit, but this should be a deliberate, checked decision, not an accident); or (c) migrate to Auth.js v5, which restructures middleware auth around a unified `auth()` helper that isn't JWT-only in the same way.

**DEPENDENCIES:** Fixing this should happen before any other admin-facing work is validated, since none of it is currently reachable to test manually.

**VERIFICATION NOTE:** This is traced from source plus authoritative external documentation with high confidence, but I could not complete a live smoke-test (attempt a real Google OAuth admin login against a running instance) in this sandbox — recommend that as the final confirmation step.



### ISSUE-002: Production deploy job can never run — branch name mismatch

**SEVERITY:** CRITICAL

**CATEGORY:** DevOps / CI-CD

**AFFECTED FILES:** `.github/workflows/ci-cd.yml`

**ROOT CAUSE:** The workflow triggers `on: push/pull_request: branches: ["master"]`. The repository's actual default (and only) branch is `master` (confirmed via `git remote show origin`). But the `build-and-deploy` job is gated by `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` — checking for a branch called `main`, which does not exist in this repository.

**IMPACT:** Every merge to `master` runs lint/typecheck/tests (whatever passes in that job — see ISSUE-006 below), builds and pushes a Docker image to GHCR with a SHA tag... and the `deploy` job's condition is simply never true, so the SSH-and-`docker compose up` deployment step never executes. Nothing is ever automatically deployed, silently.

**RECOMMENDED FIX:** One-line fix — change `refs/heads/main` to `refs/heads/master` (or rename the branch to `main` and update `on.branches` to match, if you'd rather standardize on `main`).

**DEPENDENCIES:** None — this is an isolated, trivial fix once identified. Also confirm `secrets.VPS_HOST`, `VPS_USERNAME`, `VPS_SSH_KEY`, `VPS_PROJECT_PATH`, and `DATABASE_URL` are actually populated in the repo's Actions secrets — **UNVERIFIED**, I have no access to repository settings.

## D. High Priority Issues



### ISSUE-003: 59% of API routes bypass the repository layer your own architecture doc mandates

**SEVERITY:** HIGH | **CATEGORY:** Architecture / Layering

**AFFECTED FILES:** 19 of 32 `route.ts` files under `src/app/api/`, including both webhook handlers (`api/webhooks/razorpay`, `api/webhooks/erpnext`, `api/webhooks/shiprocket`, `api/webhooks/whatsapp`), `api/admin/media`, `api/v1/wishlist`, `api/v1/invoices/[id]`, `api/v1/orders/track`, `api/v1/orders/verify-payment`, `api/search`, `api/health`, and others (full list available on request).

**ROOT CAUSE:** `src/lib/ARCHITECTURE.md` states repositories are "the only layer permitted to directly import and use `@prisma/client`." In practice, these 19 route files `import { prisma } from "@/lib/infrastructure/database/prisma"` and query it directly.

**IMPACT:** Not a runtime bug — the app works — but it means the documented architecture and the actual architecture have diverged for the majority of the API surface, which undermines the stated goals of testability and a swappable data layer, and will make future refactors harder to reason about.

**RECOMMENDED FIX:** Either formally amend the architecture doc to carve out an explicit exception for simple, single-model CRUD/webhook routes (a defensible, common real-world pattern), or migrate these 19 routes' queries into `src/lib/repositories/`. I'd recommend the former for the read-mostly/simple routes (health, search, wishlist) and the latter for the money-critical ones (the four webhook handlers), since those are exactly the places you'll want consistent, tested query logic.



### ISSUE-004: `AUTH_SECRET` is validated at startup; NextAuth actually reads a different variable

**SEVERITY:** HIGH | **CATEGORY:** Configuration / Security

**AFFECTED FILES:** `src/lib/core/config/env.ts`, `src/modules/auth/infrastructure/authOptions.ts`

**ROOT CAUSE:** `env.ts`'s zod schema requires `AUTH_SECRET` (`.min(32, ...)`) and **throws**, aborting boot, if it's missing or short. But `authOptions.ts` sets `secret: process.env.NEXTAUTH_SECRET` — a different env var that `env.ts`'s schema doesn't validate at all.

**IMPACT:** The startup check can pass (because `AUTH_SECRET` is set) while `NEXTAUTH_SECRET` — the value NextAuth actually signs/encrypts sessions with — is unset or weak. `.env.example` does list both, so a careful operator following it exactly will avoid this, but the app's own "fail loud if misconfigured" safety net doesn't actually cover the variable that matters here.

**RECOMMENDED FIX:** Add `NEXTAUTH_SECRET` to the zod schema (same `.min(32, ...)` rule), and either drop `AUTH_SECRET` or have one derive from the other, so there's exactly one secret to configure and it's the one that's enforced.



### ISSUE-005: Two high-severity npm vulnerabilities are pinned in place by `package.json` `overrides`

**SEVERITY:** HIGH | **CATEGORY:** Dependency Security

**AFFECTED FILES:** `package.json` (`overrides` block), confirmed via `npm audit` against the real installed tree

**DETAIL:** `npm audit` (real output, run against your actual lockfile in this sandbox) reports 8 vulnerabilities (1 low, 7 high). Two of the high-severity ones are specifically kept in the vulnerable range by your own `overrides`:

  - `fast-uri` — override pins `^3.0.0`; vulnerable range is `3.0.0–3.1.4` (host-confusion via backslash authority injection, GHSA-7p8r-x3mc-p8w7). The override needs to move to `>=3.1.5`.

  - `js-yaml` — override pins `^4.1.0`; vulnerable range is `4.0.0–4.3.0` (quadratic CPU consumption in `!!omap` resolution, GHSA-5p4m-2wfm-xmqj). Needs a version that includes the backport.

  Two more are transitive, not overridden: `sharp <0.35.0` (via `next`'s image optimization — inherited `libvips` CVEs) and `deepmerge-ts <8.0.0` (via `@prisma/config`/`prisma` tooling — stack exhaustion). Fixing `deepmerge-ts` via `npm audit fix --force` would downgrade `prisma` to 6.12.0, which conflicts with your recent Prisma 7 driver-adapter migration — this one needs a deliberate decision, not an automatic fix.

**RECOMMENDED FIX:** Bump the two overridden packages past their vulnerable ranges; run `npm audit fix` for `esbuild`/`fast-uri`/`js-yaml`/`sharp` (non-breaking); track the Prisma/`deepmerge-ts` one separately since forcing it breaks your v7 upgrade.



### ISSUE-006: CI test job has no database/Redis — integration and E2E tests almost certainly fail (or never really run) in CI

**SEVERITY:** HIGH | **CATEGORY:** Testing / CI

**AFFECTED FILES:** `.github/workflows/ci-cd.yml`, `src/tests/integration/*`, `src/tests/e2e/*`, `playwright.config.ts`

**ROOT CAUSE:** The `test` job runs `npx prisma generate`, typecheck, lint, and `npm run test`/Playwright, but defines no `DATABASE_URL`, `REDIS_URL`, or other required env vars, and no Postgres/Redis service containers. Your integration tests (`InvoiceService.test.ts`, `invoice-concurrency.test.ts`, `webhook-replay.test.ts`, `client-price.test.ts`, `financial.test.ts`) directly use `prisma` against a real database. Playwright's `webServer` config runs `npm run dev` in CI (since `reuseExistingServer: !process.env.CI` is false there) — that dev server would itself fail to serve any DB-backed route without `DATABASE_URL`.

**IMPACT:** Either these jobs are currently failing in CI (in which case they may be getting ignored/not blocking merges), or they're not meaningfully exercising the code they're meant to test. Given the quality of the tests themselves (see the Testing section below), this looks like a CI wiring gap rather than a testing-discipline gap — the tests are good, they're just not resourced correctly in the pipeline.

**RECOMMENDED FIX:** Add `postgres:16` and `redis:7` service containers to the `test` job (standard GitHub Actions `services:` block) and pass matching `DATABASE_URL`/`REDIS_URL` env vars, then run `prisma migrate deploy` before the test step.

## E. Medium and Low Priority Issues



### MEDIUM



**ISSUE-007 — Duplicate/dead Logger implementations, one of them unreachable.** `src/lib/infrastructure/logger.ts` (a file) and `src/lib/infrastructure/logger/index.ts` (a directory index, alongside it) both export a class called `Logger`. I verified empirically (a standalone Node resolution test) that when a file and a same-named directory sit side by side, Node/webpack resolve the **file** first — so `logger.ts` (console-based JSON logging, has sensitive-field redaction for `password`/`token`/`secret`/`card`/`cvv`/`signature`) wins for all 21 files that `import ... from "@/lib/infrastructure/logger"`, and `logger/index.ts` (properly Pino-backed, matching `ARCHITECTURE.md`, but with **no** redaction) is dead code. This also means the `pino`/`pino-pretty` dependencies in `package.json` are effectively unused at runtime. A *third*, simpler logger exists at `src/lib/utils/logger.ts` (no redaction either), used by exactly one file (`src/lib/utils/retry.ts`). **Fix:** delete two of the three, keep one, update the 22 import sites.



**ISSUE-008 — Rate limiter check sits outside the route's own try/catch in two money-critical routes.** `src/app/api/v1/orders/init-payment/route.ts` and `src/app/api/webhooks/razorpay/route.ts` both call `RateLimiter.check(...)` *before* their `try` block starts. `src/app/api/webhooks/erpnext/route.ts` does this correctly (rate-limit call is inside its try/catch). Since `RateLimiter.check` does a Redis `MULTI`/`EXEC` round trip, a Redis hiccup during checkout or the Razorpay webhook would produce an unhandled exception instead of the app's normal structured error response. **Fix:** move both calls inside their try blocks (or give `RateLimiter.check` its own internal try/catch with an explicit fail-open-or-closed default).



**ISSUE-009 — ERPNext webhook handler lacks the duplicate-delivery handling the Razorpay handler has.** `api/webhooks/razorpay/route.ts` catches the `P2002` unique-constraint error from a duplicate `webhookEvent.create` and responds appropriately (200 if already processed, 409 if concurrently processing). `api/webhooks/erpnext/route.ts` does the same `prisma.webhookEvent.create(...)` call but with no such catch — a retried ERPNext webhook delivery (normal, expected behavior from most webhook senders) will throw, and the outer catch returns a bare 500. **Fix:** replicate the same P2002-handling block from the Razorpay handler.



**ISSUE-010 — CSP is present but meaningfully weakened.** `next.config.ts` sets a real Content-Security-Policy with Razorpay-specific script/frame allowlisting (good — not a wildcard), but `script-src` includes `'unsafe-inline' 'unsafe-eval'`, which substantially reduces CSP's value against XSS, and `connect-src` allows any `https:`/`ws:`/`wss:` origin, which weakens its value against data exfiltration if an XSS is ever achieved. **Fix:** consider Next.js's nonce-based CSP support (needs wiring through `middleware.ts`, which currently only handles auth) to drop `'unsafe-inline'`; scope `connect-src` to your actual API/CDN origins.



**ISSUE-011 — Media upload endpoint has no file type or size validation.** `src/app/api/admin/media/route.ts` correctly checks `checkApiAdminOrManager()` before accepting an upload (see the note on the stale comment below), but nothing validates the uploaded file's MIME type or size before it's forwarded to S3 via `storageAdapter.uploadFile()`. Limited blast radius since it requires an authenticated admin/manager, but still worth closing. **Fix:** whitelist allowed MIME types and cap `file.size` before upload.



**ISSUE-012 — Validated `paymentMethod`/`couponCode` are computed and then discarded.** `validateCreateOrderPayload()` (`src/lib/validation/orders.ts`) trims and returns both fields as part of `validation.data`, but `src/app/api/v1/orders/init-payment/route.ts` reads the **raw**, unvalidated `payload.paymentMethod`/`payload.couponCode` instead. No functional bug today (neither field has extra rules beyond trimming yet), but it means validation logic added to one place silently won't apply to what's actually used. **Fix:** use `validation.data.paymentMethod`/`validation.data.couponCode` in the route.



**ISSUE-013 — Several status fields are raw strings instead of enums.** `PaymentTransaction.status`, `InventoryReservation.status`, `Shipment.status`, `Tracking.status`, `DeliveryAttempt.status`, `ReturnRequest.status`, `Refund.status`, `WebhookEvent.status`, `ERPSync.status` are all `String` with a comment listing allowed values, unlike `Order.status`/`Order.paymentStatus`/`Order.fulfillmentStatus`, which use real Prisma enums. No DB-level constraint stops an invalid value from being written. **Fix:** convert to enums where the value set is genuinely fixed (most of these), or add CHECK constraints via migration if you need to keep them as strings for a reason I don't have visibility into.



**ISSUE-014 — Duplicate "Shipping Policy" pages; the site links to the weaker one.** Both `src/app/shipping/page.tsx` (detailed — concrete figures: ₹999 free-delivery threshold, ₹50 flat fee, 3–7 day estimates) and `src/app/shipping-policy/page.tsx` (two generic sentences, no figures) exist as separate routes with the identical `<h1>Shipping Policy</h1>`. `src/components/Footer.tsx` links to `/shipping-policy` — the thin one. **Fix:** pick one, redirect or delete the other, repoint the footer link.



**ISSUE-015 — "Cart upsell" recommendation endpoint doesn't use cart data.** `src/app/api/v1/recommendations/cart-upsell/route.ts` returns the same 3 arbitrary non-deleted products (`take: 3`, no `orderBy`, no relation to the cart) — it's a placeholder, despite a full `Recommendation` model existing in the schema for exactly this purpose (see ISSUE-018).



**ISSUE-016 — `OutboxEvent` has no index on `published`.** The outbox-relay poller (`OutboxRelay.ts` / `api/cron/outbox-relay`) almost certainly filters `WHERE published = false`; there's no index supporting that query, which will slow down as the table grows.

## I. Security Audit



**Real strengths, verified in code (worth keeping, not just findings):**

- Both webhook handlers use HMAC-SHA256 with `crypto.timingSafeEqual` (constant-time comparison) and fail closed if the secret env var is unset.

- Checkout pricing and tax are computed **entirely server-side** from `productVariantId` + `qty` looked up against the database — the client never supplies a trusted price. This is the single most important e-commerce security property, and it's done correctly.

- Coupon validation checks `isActive`, date range, global usage limit, and per-user usage limit.

- `env.ts` validates required configuration with zod and **throws on boot** if misconfigured — good fail-loud behavior (see ISSUE-004 for the one gap in what it covers).

- Rate limiting (Redis sorted-set sliding window) is real and applied to login, checkout, and both major webhooks.

- Sensitive-field redaction exists in the (currently shadowed — ISSUE-007) logger, covering `password`/`token`/`secret`/`card`/`cvv`/`signature`.



**Gaps found (severity as scored above):** ISSUE-001 (admin lockout — not an unauthorized-access hole, but breaks the ability to administer access control at all), ISSUE-004 (env secret mismatch), ISSUE-005 (pinned-vulnerable dependencies), ISSUE-010 (CSP weakened by `unsafe-inline`/`unsafe-eval` and a broad `connect-src`), ISSUE-011 (media upload has no type/size validation).



**Also checked, no issues found:** No SQL injection surface (Prisma parameterizes everything; the one raw query in `OrderService.ts` uses a template literal with `$queryRaw`, which Prisma parameterizes safely, and it's system-generated data, not user input). No hardcoded secrets found in tracked source (`.env.example` contains only placeholders). `.gitignore`/`.dockerignore` correctly exclude `.env*`. GSTIN/phone/pincode validation uses real, correct-looking regex patterns.



**UNVERIFIED:** I did not attempt to fuzz or penetration-test any endpoint, and could not run a dependency vulnerability scan beyond `npm audit` (no SAST/DAST tooling available in this sandbox). Cron endpoint auth (see API Audit table) is unverified.
